## Problem Description

This design document will detail a system design consistent with the problem specification set for by Teleport [here](https://github.com/gravitational/careers/blob/main/challenges/systems/challenge-1.md).  This design will fulfill the requirements for level 5 of the problem description.

## Document Scope
This document will only detail a minimum viable product sufficient to meet the level 5 criteria for the provided problem description.  Out of scope are any considerations of scaling, operability, monitoring, or other operational considerations unless _explicitly_ stated in the given problem description.

## Overview
This design is composed of two components: a service which can accept and execute a "job" as defined in the problem description and a CLI which can directly interact with the job service.  The two components will interact through a GRPC API which provides facilities to start and stop a job as well as provide status and stream the output of a job.  Authentication and identity are established by mutual TLS certificate exchange using certifiates signed by a mutual authority.  Authorization is managed with simple ACLs for specific API actions.

A job is defined by some Bash-like command statement which can be executed by the service as well as additional metadata about the job.  All output from the command execution will be captured and made available back to the client through a streaming API.  Other metadata, such as exit code, will also be captured and persisted about the job and made available to the client.

## Design
This section will detail the design of each service component.

### Job Service
The job service is composed of a GRPC API layer and a job execution engine, running in the same process space.  The GRPC API will be implemented using `grpc-go` with service primitives defined in Protobuf v3 with Go binding generated by the appropriate tooling.  The job engine will be bespoke code which implement the facilities to start, stop, and stream the output from the job.  The API will call the appropriate job execution engine functionality for the API action.

Jobs will be uniquely identified by a UUID4 key which is created by the job engine as part of the initialization process for a new job.  The job engine maintains an internal state object for each job, which will also store the required data and metadata for the job.  The job engine is responsible for the persistence and retrival of job data.  The GRPC API is responsible for any business logic required to mediate between API concerns and the job execution engine.

#### Job Lifecycle
* The client calls the `create` API endpoint, providing the job command to run and other required metadata.
* The service accepts and processes the `create` request, and passes the accepted job to the job execution engine to be started by creating the required internal representations.
    * If the job execution engine cannot create the required internal state, the job will not be persisted and an error is bubbled up to the API layer which should result in the `create` API call failing.
* The job execution engine sets the job state to `starting`.  It will remain in this state as required execution environment for the job is initilized (setting up cgroups, etc).
    * If an error is encountered while initilizing the execution enviroment, the job is transitioned to `failed` and details of the failure will be provided in the job details.
* Once the execution environment is created and the job is launched within it, the execution engine changes the job state to `running`.
    * While in a `running` state all output from the job process is captured; both `stdout` and `stderr`.
* When the job process exits, the execution engine captures the exit code and either marks the job as `finished` or `failed`, depending on the exit code.
    * A `finished` job denotes that the exit code was `0`.
    * A `failed` job denotes that the exit code was other than `0`.  A description message will be provided in the job details.

A job may be stopped by the client making the appropriate API call with the job identifier at any time before it reaches either of the terminal states `finished` or `failed`.  If the job is canceled, the job is moved to a `stopped` terminal state; stopped jobs cannot be restarted.  For more details on the implementation, see section Job Cancellation.

#### Job Isolation
Jobs are isolated using cgroups v2 with hard limits for CPU, memory, and disk I/O.  The job process will not be started until the cgroups are configured, leveraging the `exec.CommandContext` to perform the required `clone3` syscall internally.  The following cgroup controllers will be used: `cpu`, `io`, and `memory`.

For ease of implementation, the CPU, memory, and disk I/O limits will be hardcoded; each job will use the same limits.  In a production system these limits would either be part of a job specification or provided by some sort of quota or allocation system.  For this MVP the following limits will be applied:
* CPU: 1 CPU (max)
* Memory: 2G (max)
* Disk I/O: 1MB/s (max), no IOPS limit

#### Job Persistance
Jobs will be persisted to service memory for the lifetime of the job service process.  No data will be persisted between executions of the job service.  In a real production system an external persistence store such as a RDBMS would be used to store and share job data between running service instances.  Such facility is out of the scope of this design.

#### Job Cancellation
To facilitate the clean shutdown of a job and any attendant processes or go-routines associated with it, the `Context` package will be leveraged.  The creation of an appropriate `Context` using `WithCancel` will be created during job initilization and passed to functions which will create processes or go-routines, including using `exec.CommandContext` when launching the job payload into the cgroup.

If the job owner wishes to cancel a running job by calling the appropriate API RPC, the job execution engine will call `Cancel` on the job's `Context` which will close the internal channel and begin the teardown process for the job process, eventually resulting in the process recieving a `SIGKILL`.  To ensure that the process and it's pipes are cleanly closed, `cmd.WaitDelay` will be set for 1s.  This will ensure that process termination does happen eventually and any go-routines that could be blocked waiting for output streaming are unblocked by closing the associated pipes.

#### Authentication & Authorization
Client authentication and identity will be established using mutual TLS authentication between the service and client.  To simplify the design, a static CA certificate will be generated and used for cert signing.  The job service will not accept certificates signed by any CA other then the static CA generated for this project. The job service will only support TLS 1.3.

Client certificates should be generated in the X.509 format and include identity information in the subject.  The job service will extract client identity from the provided certficate for autorization of actions within the API.  For simplicity the service will use the value of the subject common name in the supplied certificate as the client identifier.  Every job will be associated with the client identity provided when the job is created; this identity is the _job owner_.

Client authorization is managed by a basic allowlist gated by the provided identity.  The table below details allowlist permissions:

| API Action  | Allowed For |
| ----------  | ----------- |
| Start Job   | ALL         |
| Stop Job    | Job Owner   |
| Job Status  | ALL         |
| Job Output  | Job Owner   |

#### Output Capturing
Both the `stdout` and `stderr` of the job process will be captured to memory and persisted as part of the job metadata (including which stream the data came from).  It is important that the recieving implementation not block to prevent issues with `exec.Wait`, which will close the underlying primitives and potentally cause data loss or deadlock issues.  Output will be stored and provided as bytes.  The API component will facilitate streaming to the client either `stdout` or `stderr` or both, depending on client request.

#### API Specification
The API Specification can be found as proto3 in `proto/` within this repository.

### CLI Tool
To interact with the job service a CLI is provided.  The CLI will provide commands to start, stop, and stream the output from running jobs.  It will also provide functionality to lookup job history.  The CLI will provision the required certificate for authentication using the hardcoded CA certificate.  The CLI tools will default connect to the job server running on localhost using a hard-coded connection string.  This can be overridden by setting the `TOASTY_PIKA_SERVER_URL` environment variable to a different connection string.

#### Examples

```
# Create a new job
$> toasty-pika start "echo \"hello, world\""
Created job f325aae6-85b9-4e6c-9414-d3066edc9534

# Stop a running job
$> toasty-pika stop f325aae6-85b9-4e6c-9414-d3066edc9534
Successfully stopped job f325aae6-85b9-4e6c-9414-d3066edc9534

# Lookup details about a job
$> toasty-pika status f325aae6-85b9-4e6c-9414-d3066edc9534
Details for job f325aae6-85b9-4e6c-9414-d3066edc9534

Command: echo "hello, world"
Status: FINISHED (0)
Owner: farnsworth

# Stream output from a running job
$> toasty-pika stream f325aae6-85b9-4e6c-9414-d3066edc9534
[out] hello, world

$> toasty-pika stream 59a9b2cf-cdeb-4d4d-bf0c-d1da1e9360fd
[out] Initilizing job
[out] Connecting to external database
[out] waiting
[out] more waiting
[err] ERROR: timeout exceeded

```
